# Лабораторные 6–7. Реплицируемое хранилище

## Запуск кластера

Из корня репозитория подготовьте окружение в PowerShell.

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Откройте три окна PowerShell в корне репозитория и выполните по одной команде в каждом окне. A на порту 50051 — единственный лидер. B и C — ведомые реплики.

```powershell
.\.venv\Scripts\python.exe server.py --port 50051 --name A
.\.venv\Scripts\python.exe server.py --port 50052 --name B
.\.venv\Scripts\python.exe server.py --port 50053 --name C
```

В четвёртом окне запишите значение через B, затем прочитайте его через B в обоих режимах.

```powershell
.\.venv\Scripts\python.exe client.py --port 50052 kv-put x one --strategy QUORUM_CP --operation-id write-1
.\.venv\Scripts\python.exe client.py --port 50052 kv-get x --consistency LINEARIZABLE
.\.venv\Scripts\python.exe client.py --port 50052 kv-get x --consistency FOLLOWER_STALE --max-staleness-ms 5000
.\.venv\Scripts\python.exe -m pytest -q
```

## Что проверяется

- Лидер упорядочивает CP-записи. Он подтверждает запись после получения как минимум двух ACK из трёх с учётом собственной реплики. До этого предложенное значение недоступно для чтения. Повтор той же операции с тем же идентификатором возвращает исходный результат.
- B пересылает строгое чтение на A. Для локального чтения B периодически запрашивает у A подтверждённую версию состояния. Возраст отсчитывается от начала последней успешной синхронизации по монотонным часам B. Поэтому даже давно записанное значение можно читать, пока B продолжает подтверждать актуальность своей копии.
- Флаг `is_stale` указывает на ответ из локального снимка ведомой реплики. Он может содержать последнюю версию. Поле `read_timestamp` содержит метку времени прочитанного значения. При превышении `max_staleness_ms` ведомая реплика возвращает `STALE_READ_EXCEEDED`, в том числе для отсутствующего ключа.
- Состояние хранится в памяти. Лидер фиксирован. После полного перезапуска кластера данные нужно загрузить заново.

## Разделение сети и восстановление

```powershell
.\.venv\Scripts\python.exe -m pytest -q tests/test_cap.py
```

Тесты разделения запускают три отдельных процесса и разрывают TCP-соединения между A+B и C. Клиенты продолжают обращаться к каждому процессу напрямую. Для проверки кворумов тест читает каждую из трёх пар реплик при R=2 и отдельно читает C при R=1.

В режиме `ALWAYS_AP` узел подтверждает локальную запись одним ACK. Ведомая реплика хранит ожидающие отправки изменения и при восстановлении связи передаёт их лидеру. Для конкурирующих AP-записей побеждает большая пара `(timestamp, idempotency_key)`. При равных метках времени сравниваются идентификаторы операций. Повторная доставка обработанной записи безопасна. Пока C изолирована, её подтверждение AP-записи гарантирует только приём в память C. Ограниченное по давности чтение использует последний подтверждённый снимок. После обмена изменения доступны для чтения на всех трёх репликах.

## Замер PACELC

```powershell
.\.venv\Scripts\python.exe perf_cap_bench.py --iterations 1000 --warmup 30 --output-dir logs/cap-local
```

Скрипт сам запускает и останавливает три процесса на свободных портах. Запросы обоих режимов идут через B. Строгое чтение B пересылает на A, локальное обслуживает сама с пределом давности 5000 мс. Режимы чередуются. Для каждого режима медиана и p95 рассчитаны по успешным чтениям, доступность — по всем попыткам.

Измерения для сдачи находятся в `logs/cap/read_samples.csv` и `logs/cap/benchmark.json`, протокол тестов — в `logs/cap/test_results.json`. Таблицы и разбор экспериментов приведены в `Lab_Report_CAP.pdf`.
